# Mode M — one spec, the main context

The whole mode lives in a single file `docs/crafts/<slug>/SPEC.md` and in the main context. There are no execution subagents in M — spawning an executor means reloading the context, and that's the main token multiplier. A read-only recon agent is fine: delegate a broad "where does this live" search to an Explore subagent, it returns a list of `file:line`, not file dumps into the main context.

## 1. Brief

- Recon is cheap: pointed Grep/Glob and reading fragments, not whole files; broad search — to an Explore subagent. The goal of recon is concrete file paths for the checklist. There's a `docs/graph/` → grep by the task's topic: `active` gotcha and decision nodes are ready-made lines of the spec's "Constraints" (skip `superseded` nodes — history, not live constraints; a `verify` node carried in keeps its mark, "constraint in doubt"). **Parent-artifact hook:** the statement points at a `docs/crafts/<slug>/BRIEF.md`, or the task's slug is a leaf in some `docs/crafts/*/PLAN.md` (one glob+grep — only when such artifacts exist) → read the parent first and carry its constraints and rejected options into "Constraints" (a rejected option resurfacing in code is exactly what wrap's graph node records as "alternatives considered"). Don't relitigate the parent's decision.
- Fill in the spec per `templates/SPEC.md` and place it in `docs/crafts/<slug>/SPEC.md` (slug = the task's slug; a folder per task — no name collisions, you don't touch others' specs). Cap — in the `templates/SPEC.md` file-form (M's limit): doesn't fit — means you're writing a novel, not a spec. Checklist items — with concrete, recon-confirmed file paths; a later item may carry `path: TBD after item N` — never invent a path for the format's sake. The "Non-goals" section is mandatory: an anchor against scope creep.
- Don't turn reasonable assumptions into questions — fix them in the "Assumptions" block at the top of the spec. The explicit ok covers the assumptions the user read and left untouched — that's why they sit at the top, the first thing seen; an untouched assumption is approved by the ok, not "silently consented".
- **One approval round-trip:** in a single message show the full spec draft and a batch of questions (at most 5 — only those where the answer really changes the solution). The user's answer closes the questions and serves as the "ok" — this is the confirmation gate (the rule and the advance ok are in the router); silence or a missing answer ≠ ok.
- The answers arrived → check de-escalation first, while the spec is still a draft: every question closed by the user's answers, the scope shrank to ≤2 files, no risk zone → this is S — de-escalate per the router's rule (it deletes the draft). Otherwise: write the answers into the spec, set status `in-progress`, create the branch (the rule is in the router) — and only now execution.

## Entering from escalation (after-the-fact)

An S task escalated mid-work → the spec starts from reality, not from scratch: work already done → checklist items ticked right away; decisions already applied in S → "Assumptions" tagged `already applied`; recon — only over the remainder. Then the usual single round-trip: the shown draft covers both the done and the remaining, one ok legitimizes both. (An escalation from S's step 1 — questions at the restatement, nothing built yet — is just the normal brief above, no special path.)

## 2. Execution

- Go down the checklist top to bottom. Tests — the router's global rule: failing test first, bugfix = repro-first, no theater.
- **An atomic commit per checklist item**; the checkbox is ticked right away, and the spec goes into the same commit — state rides with the branch (resume in another worktree or on another machine), progress reads from the git log. Stage with an explicit list (`git add <files>`), not `-A`: nothing foreign should land in the commit. Separate summaries aren't needed.
- Ambiguity along the way: changes behavior or architecture → stop and a concrete question to the user; doesn't change → an assumption into the "Assumptions" block tagged `post-ok` and continue — the wrap will surface these (step 5): the ok covered the spec the user saw, not what grew after it. Don't expand scope silently — check against the "Non-goals".
- Felt like doing something "while we're at it" → a line into the spec's "Open questions", not code. Noticed something foreign, outside the task's scope (a bug in a neighboring module, a stale doc), → a line into `docs/crafts/_backlog.md` (format — `templates/BACKLOG.md`) and continue.
- A fix hypothesis failed → the router's no-guess-and-patch rule, counter included; the hypothesis log — in the spec's "Log"; the found root lands as a fix + regression test.

## 3. Wrap — closing with proof

The verification-honesty rule is the router's ("done" = observed, "should work" is forbidden). The block is mandatory in full:

1. A full run of tests and lint; the suite doesn't run locally (CI-only, hour-long) → run the affected subset and say so in the report. Behavior is visible to the user → run the scenario live (dev-server/CLI). Red that's not your fault → record it in the "Log", don't fix it silently.
2. Go through the diff against the acceptance criteria **line by line**: for each criterion — where and by what it's satisfied. At least one unsatisfied → the work isn't finished.
3. A review pass over the diff: edge cases, error handling, security, forgotten debug traces. This is the author's self-review — cheap but biased (same head that wrote it); the lens list here is a mnemonic, the canon is `code-review`'s. The risk zone was touched → a separate pass by a fresh subagent over just those spots — hand it the diff of those spots plus the relevant criteria, not the whole context — and offer an independent `code-review` of the branch (a fresh framing with a skeptic, which self-review can't be); by user request too. Any wrap step produced a fix → re-run 1–2 for what it touched: old green doesn't cover new code.
4. **CRAFT.md, the graph, the glossary — the router's global rule feeds here.** Plus the backlog sweep: scan `docs/crafts/_backlog.md` for `graph-candidate` lines → the worthy ones become graph nodes (the `file:line` proof rides along); **consume the breadcrumb** — replace the promoted line with a pointer `→ [[slug]]`, don't leave it to re-promote next time; the rest stay untouched.
5. Spec status → `done`, a paragraph in "Outcome": what was done, deviations from the plan, how it was verified — plus counters: round-trips with the user, escalations, closed checklist items. Assumptions tagged `post-ok` → list them explicitly in the closing report: the ok covered the spec the user saw. The spec stays in `docs/crafts/<slug>/` — no need to move it anywhere. The task is a leaf of a PLAN → tick its checkbox there. Unresolved "while we're at it" ideas from "Open questions" → pour them into `docs/crafts/_backlog.md` or discard them deliberately: in a done spec they'll die. Propose a PR and wait for the yes — proposing is not creating; the PR body is the spec's "Outcome" section, don't compose it anew.

## Escalation to L

The checklist has grown past ~12 items, or the context is visibly degrading (a compaction happened; you're re-reading files you've already read to stay oriented) → group the existing checklist into phases, change the mode in the spec to L, and continue per `modes/l.md`. The spec is the same, no restart. Parallelizability is not a trigger here either (the router's rule): it's an execution strategy you gain access to inside L, not a reason to enter it.
